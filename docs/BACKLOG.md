# Patchbay — Backlog

A modern replacement for RDCMan (Sysinternals). WPF on .NET 10, hosting the
Microsoft RDP ActiveX control (`mstscax.dll`) via `WindowsFormsHost`.

**Effort key** — `S` ≤ half a day · `M` ≈ 1 day · `L` 2–3 days · `XL` a week or more.
**Flags** — `[risk]` likely to overrun, `[sec]` security-sensitive, `[spike]` timeboxed investigation, `[cut]` part of the days-not-weeks first cut.

Milestones M0–M5 and M7 are v1. M6 is deliberately held to v1.1 — see the note there.

- [x] `M1-14` Import individual `.rdp` files — **M** — a second parser was the small half. A `.rdg` is a document somebody built and kept; a `.rdp` arrives — emailed by a supplier, downloaded from a portal, left on a share — and the format can say a great deal more than "here is a machine to connect to". It can hand the far end every drive on this computer, the smart card in its reader and the microphone; it can name a program to run instead of a desktop; and it can ask the client not to check who it is connecting to. In October 2024 a campaign used signed `.rdp` attachments to do the first of those at scale.

  **So the rule is one sentence: an imported file may switch a redirection off, but it may not switch on one that Patchbay leaves off.** Off is never an attack, so a file asking for less than the default gets it. What counts as off is read from `ConnectionSettings.Defaults` rather than a list written out beside the rule, which is what keeps it true if a default ever moves — and it is why the clipboard falls out on its own rather than needing an exception: Patchbay already allows it, so `redirectclipboard:i:1` is imported and changes nothing, while `drivestoredirect:s:*` is refused. Refusing something the default already grants would be theatre — it would change nothing about the connection and would put a warning on the screen saying otherwise. Nothing is dropped in silence: everything refused is named, and turning any of it on is a checkbox in the inspector, which makes it a decision by the person rather than by the file.

  Three more things a file does not get to decide. `authentication level:i:0` is "connect anyway, and say nothing", so it is not imported and the connection keeps what it inherits — a session to a server that could not prove who it is looks pixel for pixel like a session to one that could. The address goes through `NodeValidator.IsValidHost`, the same check as one somebody typed, so a file cannot put into the tree what a person could not have typed into it. And display names and any text quoted back into a warning are stripped of control and Unicode formatting characters, because a right-to-left override in a file name reads in the tree as an entirely different machine from the one it connects to. A start program is quoted rather than counted: Patchbay opens desktops, so `alternate shell` and the RemoteApp settings are never imported whatever they say, and a file that arrived from somewhere else and names a program to run is the part worth reading before connecting.

  **The parse has two properties worth naming.** The encoding comes from the byte order mark, because `mstsc.exe` writes UTF-16 and reading one of its files as UTF-8 produces a NUL between every letter, every line failing to parse, and an import that reports nothing wrong and produces nothing at all. And a binary value is not kept: `password 51` is a DPAPI blob belonging to whoever saved the file, and the surest way for it never to reach a node name, a warning or a log line is for `RdpFile` not to hold it. The size bound is checked while reading rather than after, so a file made of one very long line is refused rather than allocated.

  Shape decisions the format forced. A `.rdp` carries no display name, so the connection is named after the file — what the person who saved it called the machine, and more use in a tree than the address written out twice. One connection does not go into a folder of its own: `ImportResult.RootIsWrapper` says the group around it is scaffolding rather than structure, which is a distinction a `.rdg` needs kept, since its root group carries the settings its children inherit. Several files import at once, because a `.rdp` holds one connection and somebody moving off `mstsc.exe` has a folder of them; they share one collation, so twenty files asking for the same redirection produce one sentence rather than twenty, and one bad file among twenty is a warning rather than the end of the import. `ConnectionImport` routes on the extension and refuses one it does not know rather than sniffing the contents — sniffing a file that arrived from somewhere else, to decide which parser to hand it to, is a way of letting the file choose.

  56 tests, and 34 checks against the real `Default.rdp` this machine's own `mstsc.exe` wrote — UTF-16, read in 27 ms. That file is why the rule is not a straw man: an ordinary saved connection asks for printers and the smart card reader, so the refusal fires on a file nobody built to be hostile. Also verified there: detection asked for and imported as detection, the four "disable" settings read back as their opposites, a domain split out of `CORP\user`, `host:3390` split into an address and a port while `fe80::1` is left alone, and gateway mode 3 — "whatever a policy on this machine says" — left to inherit rather than guessed at
- [x] `M1-15` Import mRemoteNG `confCons.xml` — **M** — **written against the format, and nothing of theirs is in this repository.** mRemoteNG is GPL-2.0 and Patchbay is GPL-3.0-or-later, which are incompatible in that direction: lifting even a helper out of their tree would bind this repository to terms it has not chosen, and the remedy would be relicensing rather than deleting a file. Reading a file format is a different act, and it is the one that was performed. `THIRD-PARTY-NOTICES.md` now says that for all three importers rather than promising it for the ones still to come.

  **The inheritance maps better than RDCMan's did, and that is the whole reason this was the easy one.** A `.rdg` carries `inherit="FromParent"` per block of settings; mRemoteNG carries an `Inherit*` attribute per setting, which is Patchbay's own rule written in somebody else's vocabulary. `InheritColors="true"` becomes a null colour depth, nothing is resolved at import time, and what somebody had set up goes on working the way they set it up.

  **This is an inventory, not an invitation, so `M1-14`'s rule is deliberately not applied.** A `.rdp` is one connection circulating as an attachment, so it may switch a redirection off but never on. A `confCons.xml` is somebody's whole estate, imported because it was asked for, and quietly dropping the drive redirection they configured on forty connections would be losing their work rather than defending them. What it gets instead is a count — how many connections hand over drives, the smart card reader, ports or the microphone; how many connect without checking the server's identity; how many switch off network level authentication. That leaves a residual risk, which is named in the threat model rather than papered over: a hostile inventory can turn a redirection on, for this format and for `.rdg` alike. What makes it a different bet is that importing somebody's whole estate is already an act of trusting them wholesale, where opening a single attached connection is not.

  **Passwords are counted and never decrypted, and here that is a decision rather than a limitation.** RDCMan's blobs and a `.rdp`'s `password 51` are DPAPI-protected to whoever saved them, so the rule has been a constraint dressed as a policy — they could not be read if Patchbay wanted to. mRemoteNG encrypts under a key derived from a password that defaults to a value published in its own documentation, so these could be. Reading somebody's credential store because the key is guessable is a thing to do deliberately, with the person watching, and not in the middle of an import.

  Three smaller things the format forced. The protocol is followed up the tree rather than assumed, because a folder that says SSH with connections that inherit is an ordinary file and reading each of those as RDP would fill the tree with connections that cannot work. Full file encryption is caught before the parse rather than after — what mRemoteNG writes then is not XML at all, and "this file is not valid XML" sends somebody hunting a corrupt file when what they have is a working one they need a password for. And `.xml` is the one extension that names no format, so the router hands it to this reader, which refuses anything whose root element is not its own: a reader checking its own input rather than a router guessing from the contents.

  42 tests, 1036 in all

## M3 — Credentials

- [x] `M3-01` Credential model + named, reusable `CredentialProfile` — **M** — the store was already there: M3-02 protects a secret into a string and reads it back, so what was left was deciding where the string lives and how a profile is referred to.

  Profiles sit beside the tree on `ConnectionDocument`, not in it. A profile is not a place to connect to, and putting it in the tree would make it inherit settings and turn up in search results. Nodes point at one through `CredentialProfileId`, which was already on `ConnectionSettings` and already inheritable, so a group can name the account its servers use and one edit changes fifty machines. No schema bump: a document written before this existed reads back with an empty list, which is what it meant.

  `CredentialVault` owns both directions, so the protector has exactly one caller. Spreading protect and unprotect around the application is how a plaintext password ends up assigned straight to `ProtectedPassword` by a screen that meant well, and nothing about the document looks wrong until somebody opens it in a text editor. Reading never throws — a deleted profile and a password from another Windows account are both ordinary outcomes of opening a file that has moved. Writing does throw, following M3-02: a failed protect must not fall back to plaintext, and a failed save leaves any previous password alone rather than half-writing over it.

  Four outcomes, and the two that went wrong still carry a usable sign-in. `Resolved` covers a profile with a password and a profile without one, because the difference is `HasPassword` and a profile with nothing saved is configured correctly and simply needs asking (M3-05). `NoProfile` is prompt and current-user connections, where the account name is left to the mapper, which already falls back to the node (M4-10). `ProfileMissing` covers both a deleted profile and one that was never named, because the same thing has to happen next either way. `PasswordUnreadable` is the one with a rule attached: the stored value must be left exactly as it is, since a blob this account cannot open is very likely one another account can, and overwriting it loses somebody else's password to save a round trip.

  Wired into the connect path, so this is not a model nothing uses. The shell resolves before opening a tab and hands the result to `SessionRequest.Credentials`, and a missing profile or an unreadable password says so in the status bar rather than arriving as a logon prompt nobody expected. The connection still goes ahead in both cases: the session comes up showing its own logon screen, which is what M3-06 will put a panel over. Real DPAPI is passed in from `App.xaml.cs`; the view model defaults to the protector that refuses, so a shell can be built without reaching the platform.

  28 tests. `CredentialProfileId` was `SettingKind.Hidden` here — a text box full of GUIDs is worse than no control — and became a picker with `M3-10`, which is also where creating and deleting profiles landed. Deleting is why `NodesUsingCredential` exists, and why it reports only nodes that name the profile themselves rather than every server that inherits it
- [x] `M3-02` DPAPI `CurrentUser` protect/unprotect for stored secrets — **M** `[sec]` `[cut]` — the primitive, before anything has a secret to put through it. `ISecretProtector` and everything around the platform call live in `Core`; the two lines that are actually Windows live in the shell, because `ArchitectureTests` says where the implementation goes.

  A protected secret is written as `pb1:dpapi:BASE64`, and the marker earns its keep three times. A field holding a password and a field holding a blob are both strings, so without one the only way to tell them apart is to try decrypting, which destroys a password that happens to be valid base64. A document will hold blobs from more than one store at once, since Credential Manager (M3-04) and a master password (M3-07) arrive one secret at a time — and both have now stopped being predictions: a document put behind a master password keeps every blob it could not read as it was, permanently, and a document moved to Credential Manager does the same. Three schemes read, one writes. And a file written by a later Patchbay has to be refusable politely rather than reported as corrupt.

  Reading fails in five distinguishable ways because they are five different sentences. `WrongScheme`, `TooNew` and `Unreadable` all mean leave the stored value alone, and collapsing them is how somebody who signed in as a different Windows account gets told their connection file is damaged. Writing is the one direction that throws: `UnavailableSecretProtector` refuses rather than falling back to plaintext, because the fallback is invisible — nothing on screen changes and the only difference is a cleartext password in a file that gets backed up and attached to support tickets.

  Two things about DPAPI itself. The scope is chosen when protecting and travels inside the blob, so passing `LocalMachine` to `Unprotect` opens a `CurrentUser` blob happily — that argument is not a check and nothing relies on it. And the entropy is a constant in the binary, so it is not a secret; it buys only that another program running as the same user cannot open a Patchbay blob by handing it to DPAPI and seeing what falls out. Nothing here defends against code running as the signed-in user, because that is DPAPI's contract. That is `M3-07`'s job, and it is done.

  Binding a blob to its node id was considered and rejected: duplicate (M2-09) and import both move a secret between ids, and it would silently break the copy. 46 tests in `Core`, plus 33 checks against real DPAPI covering tamper, truncation, foreign entropy, a 4 KB secret and every not-ours case. Cross-account and cross-machine unreadability cannot be tested from one account and are on the `M4-17` matrix
- [x] `M3-03` In-memory secret handling: pinned buffers, zero on dispose — **M** `[sec]` — a `string` cannot be erased. It is immutable, it may be interned, and a compacting collection can copy it somewhere else and leave the old bytes behind with nothing pointing at them. So a password that arrived as a string at nine in the morning is still legible at five and no code in the process can change that. `Secret` is what Patchbay holds instead.

  The buffer comes from the pinned object heap, and pinning here has nothing to do with interop: a buffer that has been moved cannot be erased, because erasing writes over where it is and not over where it has been. Verified rather than assumed — across a forced compacting gen-2 collection an ordinary array moved and a pinned one did not. The bytes are UTF-8 because that is what `M3-02` already protects and stores, and changing the encoding would make every password saved by an earlier version unreadable, which is worse than any encoding argument is worth.

  It goes the whole way through rather than stopping at the store, because the copy that mattered was the one at the far end. A session keeps its sign-in for as long as the tab is open — deliberately, since `M3-05` reuses it to reconnect a dropped link without asking at three in the morning — so that was the longest-lived plaintext in the application and the one worth erasing. The protector now takes bytes and hands bytes back, so a password read out of the store never becomes a string at all; before this it was decoded with `Encoding.UTF8.GetString` and that string stayed in the heap for the rest of the run.

  Erasing destroys the plaintext and not the identity, which is the decision the rest depends on. A `Secret` keeps an HMAC-SHA-256 fingerprint under a key made fresh each time the process starts, so it can still say whether something equals it once the password is gone. That is what lets a session erase a refused sign-in the moment a different one arrives while `M3-06`'s prompt goes on refusing to resubmit it, and it is what keeps record equality on `SessionCredentials` working, which `M4-08` and the re-prompt both rely on. The per-process key buys one thing: a fingerprint that got out could not be looked up in a table of hashed common passwords, or matched against one from another run.

  Reading an erased secret throws instead of returning an empty password. A session that silently connects with nothing is a bug that looks exactly like a wrong password, and it would be chased at the far end for as long as that took.

  Ownership is one rule: whoever the secret was given to erases it. Copies made with `with` share the buffer, which is safe precisely because comparing does not need the plaintext. A sign-in that never reached a session is not erased and waits for a collection, the same as before.

  Widened the `M3-11` gate while here. A type holding a `Secret` is exempt from having to override `ToString`, because the generated one prints the mask — which is an argument for the type rather than a hole in the test, and there is a test for that too. Types holding a `Secret` are counted, so moving a password onto one cannot quietly shrink what the gate examines; it caught this change immediately, dropping from four secret-holding types to two.

  20 new tests, 829 in all, plus 29 checks against real DPAPI covering the byte-span API, awkward plaintexts, a 4 KB secret, a tampered blob and erasure through the whole path. What is not fixed and cannot be here: the control takes a BSTR, so `RevealAsString` has to exist and is called at the dispatch site and nowhere else; `PasswordBox.Password` hands out a fresh string on every read and WPF owns those; and nothing locks the pages out of the swap file, which needs `VirtualLock` and is not built
- [x] `M3-04` Windows Credential Manager as an alternative store — **L** — the same cryptography under a different roof, and worth building anyway. A Credential Manager entry is protected by the same user-scoped Windows data protection a `dpapi` blob is, so this is not stronger and defends against nothing the other one lets through. Choosing between them on strength would be choosing at random.

  **What changes is where the ciphertext is.** With `dpapi` the document carries it, so a file put on a share, attached to a ticket or committed by accident carries an encrypted password with it — useless to whoever picks it up, and theirs to keep and attack offline for as long as they like. With `wincred` the document carries sixteen bytes of identifier and Windows keeps the password, so a copy of the file has no password material in it at all. Verified rather than assumed: the saved file holds `pb1:wincred:` and no plaintext, and `cmdkey /list` shows `Patchbay/{document}/{entry}` with "Patchbay saved password" in the account column — identifiable, and carrying none of the person's own server or account names.

  The cost is the mirror image and is why this is offered rather than made the default: the document stops being sufficient. Restore it on a fresh machine and the connections are all there and none of the passwords are, where a `dpapi` document at least still holds them for the account that wrote it. `SecretUnprotectStatus.Missing` is a new status for exactly that, and it is not `Unreadable` dressed up — absent and shut are different problems with different places to go and look, and the one thing `Unreadable` could never say is "check whether it was deleted in Windows".

  **A reference is not a secret, and the difference is a method on the interface.** Every store before this one put the ciphertext in the document, which made the document the only record: clear the field and the password is gone. Here clearing the field leaves the password in Windows with nothing left that knows it is there. So `ISecretProtector` grew `Forget`, a no-op in the base class and the whole of the difference in one implementation, and every place that stops referring to a saved password calls it — replacing one, clearing one, deleting a profile, moving between stores. Ordering matters in two of those: the release comes strictly after the replacement has landed, because doing it first and then throwing loses the password, and `Reprotect` releases only what actually moved, because what did not move still refers to entries that are still wanted. Deleting a profile is why `CredentialOperations.Delete` takes a vault now — required rather than optional, since the caller who forgets it leaves a password in Windows and nothing about the result looks wrong.

  **Entries are filed under the document, and that is a safety property rather than tidiness.** Patchbay opens one file at a time but a person may have several, all filing entries in the same Windows store. A sweep that deleted every Patchbay entry the open document did not mention would delete the other document's passwords, silently, as a tidying-up operation. So the target name carries a document id, a sweep never sees past it, and the failure mode is a stranded orphan rather than a destroyed password — which is the correct direction to be wrong in. That id is what forced **schema 3**: a build that dropped it would write the file back without one, the next load would mint a fresh one, and every password that document keeps in Windows would be filed under an id nothing refers to. `credentialStore` did not force it and does not get one of its own — dropping a preference loses a preference, and every blob already written still names the scheme that wrote it.

  **Reads route by scheme, writes still do not** (`M3-02`, `M3-07`), and this is the item that made the routing carry three schemes rather than two. - [x] `M3-07` Optional document master password (AES-GCM + PBKDF2/Argon2id) — **L** `[sec]` — the answer to the gap the threat model named against itself: DPAPI protects a saved password against the file moving and against nothing else, because a local administrator can read another account's store and the signed-in account's own code is inside the boundary by design.   **Two keys, not one.** The master password derives a key-encryption key with PBKDF2-HMAC-SHA256 at 600,000 iterations over a fresh 16-byte salt; that wraps a separate 32-byte random document key with AES-256-GCM; the document key encrypts each saved password, again AES-256-GCM under a fresh 96-bit nonce. Changing the master password rewraps thirty-two bytes instead of re-encrypting every secret — which matters because a crash halfway through the alternative leaves a document with some passwords under the old password and some under the new, and nobody can fully open it again. - [x] `M4-08` Auto-reconnect: exponential backoff, attempt cap, cancel, visible countdown — **L** — the control already does half of this, better than Patchbay can. `EnableAutoReconnect` is on by default from `IMsRdpClientAdvancedSettings2` up, and a momentary transport loss makes the control rejoin the session it already has with the cookie the server issued: desktop, open windows and half-typed command intact, where a fresh connect gets a new session. So there are two layers covering different failures. The control's reaches a wireless blip; Patchbay's reaches a reboot, a gateway restart, or a laptop shut for an hour.

  Starting a sequence is narrow, continuing one is wide. Only a working session breaking starts one, because an attempt that never got anywhere has somebody watching it with a button underneath, and silently retrying a name that has never resolved only delays the truth. Once running, an outright failure continues it: a rebooting machine refuses connections for a minute before accepting one. Anything anybody decided stops it — a disconnect that was asked for, an attempt called off, a sign-out, and a session that ended with no stated reason.

  A refused sign-in is checked before the counting, so it stops a sequence already in flight. The case is the first reconnect after a drop reaching a machine whose password has since changed; without the check the remaining nine attempts lock the account out with nobody at the keyboard. It is also the one fact a transition cannot carry, which is why `IRemoteSession` grew `LastLogonError`. The counter resets on success, or a connection that drops once a fortnight and recovers every time is called exhausted after ten fortnights.

  Jitter is not decoration: a gateway restart takes every session through it down at the same instant, and without a spread they come back in lockstep at the machine that has just come up. Supplied as a sample rather than drawn inside, so the arithmetic stays a function of its inputs. Ten attempts at 5, 10, 20, 40 then 60 seconds is a little over seven minutes, which covers a reboot and stops short of hammering a decommissioned server.

  Decision, arithmetic and countdown live in `Core`; the shell owns only the clock, because a visible countdown is redrawn on the thread that draws. Each tab measures its own elapsed time — a shared stopwatch charged a countdown joining a clock already running for the part of the interval that passed before it existed, costing up to a second of its first wait, and the end-to-end harness caught it.

  `OnAutoReconnecting2` (34) and `OnAutoReconnected` (33) are sunk; `OnAutoReconnecting` (17) is not, because its third parameter is an `[out]` the control reads back to decide whether to keep trying, and answering it wrongly stops the reconnect silently. A certificate alone is reported as no more than TLS, even though NLA over NTLM outside a domain is indistinguishable from here — the field is read as an assurance, so it under-reports on purpose. Zero is read as "the engine did not say" rather than as legacy RDP security, because zero is also what the property reads before anything has connected; guessing wrong would put a red badge on every session, and an alarm that is always wrong is one people stop seeing.

  The hazard was not the COM call, it was the printing.   The attempt now outranks the document for who is signing in. That matters in one situation: somebody refused, asked again, and typing a different account, where sending the stored name back would retry what was just turned down. The domain travels with the user name and not on its own, because an empty domain is how a local account is expressed and falling back to the document's realm fails in the way that most looks like a bad password.

A wrong password and a refused account are worth asking about; locked, disabled, expired, out-of-hours and barred-from-this-machine are not. Expired and must-change count as unusable rather than wrong, which is the judgement call: what is on file may be correct and what is needed is a change at the far end. Anything unpinned stays `Unknown` and still permits asking, since a person typing once more is not the lockout risk an automatic retry loop is.

No transition either way.   A session cannot connect until something has given it a window. The control has no COM object until its handle exists and no handle until it is in a window on screen, and the shell adds a tab and connects it in one go while WPF realises the tab a moment later. So `ConnectAsync` waits for the handle, and waiting is what makes it work: awaiting yields the dispatcher, which is what lets the realisation happen.
