# Patchbay — Backlog

A modern replacement for RDCMan (Sysinternals). WPF on .NET 10, hosting the
Microsoft RDP ActiveX control (`mstscax.dll`) via `WindowsFormsHost`.

**Effort key** — `S` ≤ half a day · `M` ≈ 1 day · `L` 2–3 days · `XL` a week or more.
**Flags** — `[risk]` likely to overrun, `[sec]` security-sensitive, `[spike]` timeboxed investigation, `[cut]` part of the days-not-weeks first cut.

Milestones M0–M5 and M7 are v1. M6 is deliberately held to v1.1 — see the note there.

## M3 — Credentials

- [ ] `M3-01` Credential model + named, reusable `CredentialProfile` — **M** — the store this needs is already there: M3-02 protects a secret into a string and reads it back, so what is left is deciding where the string lives and how a profile is referred to
- [x] `M3-02` DPAPI `CurrentUser` protect/unprotect for stored secrets — **M** `[sec]` `[cut]` — the primitive, before anything has a secret to put through it. `ISecretProtector` and everything around the platform call live in `Core`; the two lines that are actually Windows live in the shell, because `Core` is platform-neutral and `ArchitectureTests` says where the implementation goes. A protected secret is written as `pb1:dpapi:BASE64` and that shape earns its keep three times over: a field holding a password and a field holding a blob are both strings, so without a marker the only way to tell them apart is to try to decrypt one — and a password that happens to be valid base64 gets destroyed; a document will hold blobs from more than one store at once, because Credential Manager (M3-04) and a master password (M3-07) arrive one secret at a time, so a blob has to name the key that opens it; and a file written by a later Patchbay has to be refusable politely rather than reported as corrupt. Reading fails in five distinguishable ways and they are separate because they are separate sentences — `WrongScheme`, `TooNew` and `Unreadable` all mean leave the stored value exactly where it is, and collapsing them is how somebody who signed in as a different Windows account is told their connection file is damaged. Writing is the one direction that throws: `UnavailableSecretProtector` refuses rather than falling back to plaintext, because the fallback is invisible — nothing on screen changes and the only difference is a cleartext password in a file that gets backed up, copied to a laptop and attached to a support ticket. Being on Windows is not the same as having working DPAPI (an account with no loaded profile has no master key), so availability is established with a two-byte round trip on first use rather than assumed, and the offer to save a password is never made on a machine that cannot keep one. Two things worth knowing about DPAPI itself. The scope is chosen when protecting and travels inside the blob: passing `LocalMachine` to `Unprotect` opens a `CurrentUser` blob perfectly happily, so that argument is not a check and nothing relies on it — what stops another account reading the blob is the key. And the entropy is a constant compiled into the binary, so it is not a secret; it buys only that another program running as the same user cannot open a Patchbay blob by handing it to DPAPI and seeing what falls out. Nothing at this layer defends against code running as the signed-in user, because serving that user is DPAPI's entire contract — that is M3-07's job. Binding a blob to its node id was considered and rejected: duplicate (M2-09) and import both move a secret between ids, and it would silently break the copy. 46 tests in `Core`, plus 33 checks against real DPAPI on this account covering tamper, truncation, foreign entropy, a 4 KB secret and every not-ours case. Cross-account and cross-machine unreadability cannot be tested from one account and goes on the `M4-17` matrix
- [ ] `M3-03` In-memory secret handling: pinned buffers, zero on dispose — **M** `[sec]` — M3-02 zeroes every byte array it makes but hands the secret back as a `string`, which it cannot zero. Shortening that string's life is this task; abolishing it is not possible, because the RDP control takes its password as a BSTR and cleartext exists in managed memory at connect time whatever the store does

## M4 — RDP engine

- [x] `M4-01` `IRemoteSessionHost` abstraction + fake impl so UI builds without RDP — **M** `[cut]` — lives in `Core`, so the tests reach it without a Windows target; nothing visual crosses the seam, and the fake makes refusal, cancellation and a dropped session into properties you set
- [x] `M4-02` COM interop for `MsTscAx`; detect `IMsRdpClient` 9/10/11 at runtime — **L** `[risk]` `[cut]` — there is no `IMsRdpClient11`; 11 was a coclass number, and the scriptable chain stops at 10. Every GUID is read from the type library in `mstscax.dll`, and the control is chosen by creating it rather than by reading the registry, because the newest coclass registered on a current Windows 11 cannot be created at all. The interfaces are dispinterfaces with no members, so there is no vtable to get wrong; everything else goes by name. Probing moves itself to an STA thread — the non-scriptable interfaces have no proxy, so an MTA probe reports no credential support on a control that has it
- [x] `M4-03` `WindowsFormsHost` embedding + airspace-safe layout rules — **L** `[risk]` `[cut]` — the rule is swap, never stack: `SessionSurface` collapses the session to show anything else, because in-window WPF content drawn over a hosted HWND is simply not visible. Popups, tooltips and context menus are the exception and are fine — they get their own top-level window. `AirspaceRules` checks placement on load rather than trusting it, since all three failures (ignored opacity and transforms, escaped clipping, and a layered window rendering nothing at all) are silent and none of them looks like a layout mistake
- [x] `M4-04` Settings mapper: model → `AdvancedSettings` (full property surface) — **L** — a **plan**, not a sequence of calls. Every write goes out late-bound, so none of it is checked by a compiler; what a test can check is a list, so `RdpSettingsMapper` builds one in `Core` — no COM, no Windows target, no control — and `RdpSettingsApplier` in `Patchbay.Rdp` walks it. Everything worth getting wrong is in the list: which settings object a property lives on (the gateway is on `TransportSettings` and nowhere else), which number a mode is, and whether a redirection somebody switched off is actually sent. The spellings are traps and all three are now asserted — `GatewayHostname` has one *n*, `ColorDepth` is American where the model is not, and `overallConnectionTimeout` and `singleConnectionTimeout` both start lower case; a control given only the second keeps retrying past the deadline someone set. `ConnectToAdministerServer` falls back to `ConnectToServerConsole`, which is what `Alternatives` is for. **The rule the report turns on is material versus not.** A resolution that did not apply announces itself the moment the session draws; a clipboard redirection that did not get turned *off* announces itself never, and the person carries on believing the opposite of what is true — so turning a redirection off is material and turning it on is not, silencing audio is and un-silencing it is not, and every gateway write is, because a gateway that did not apply either fails the connection or quietly goes direct to a machine somebody meant to reach through one. `IsClean` and `IsSafe` are therefore different questions, and the notice stays silent about the failures that do not matter: a warning shown every time an older control declines a colour depth is one people learn to dismiss unread, and the one that mattered goes with it. Unsupported and rejected are kept apart — the control being old and the control objecting are different conversations, and only one of them is Patchbay's fault. Deliberately absent: passwords (the document holds none, and handing one to the control is `M4-10`), and smart sizing, which stopped being a document setting the moment a tab could toggle it — `M5-09` owns it, and a reconnect that put the saved value back would undo what somebody had just chosen. The settings-object walk moved out of `RdpSessionControl` into `RdpSettingsObjects`, so there is one copy. `M4-13`, `M4-14` and `M4-11` are each one more entry in the table when the model grows the setting. Verified against the real control (mstscax 10.0.26100, `AdvancedSettings9` / `SecuredSettings3` / `TransportSettings4`): all 17 writes applied and every one read back as written, a name the control does not have reported `Unsupported`, a bad value on a real name reported `Rejected`, and a missing primary name applied through its alternative. **Correction, from the `M4-14` verification:** of the three spellings called traps above, only `ColorDepth` is one — `GatewayHostname` and `overallConnectionTimeout` differ from the model by case alone, and dispatch lookup ignores case, so neither would ever have missed. The rule is that a difference of *letters* is dangerous and a difference of *capitals* is cosmetic. **Second correction, from `M4-10`:** passwords are no longer absent from the plan. What stays true is the reason they were — the write comes from the `SessionRequest` and never from `ConnectionSettings`, so there is still no path by which saving a connection file writes a secret into it — and the plan entry carries `IsSecret`, which the report and every printer of a write now respect
- [x] `M4-05` Connect / disconnect lifecycle state machine — **L** `[cut]` — the transition table lives in `SessionStateMachine` in `Core` and is written out in full in its tests, so a move that ought to be refused cannot quietly stop being refused. Two ways in: `MoveTo` throws, for moves Patchbay decides, and `TryMoveTo` returns false, for anything the control announces — a disconnect reported twice is the world repeating itself, not a bug. A drop by the far end is a disconnect and never a failure; offering a retry to someone who meant to log off is the mistake it exists to prevent. The `IRemoteSession` that drives a real control needs `M4-06` first
- [x] `M4-06` Event wiring: Connecting, Connected, LoginComplete, Disconnected, FatalError, LogonError — **M** — the six arrive as a `SessionSignal` and are read by `SessionSignalRouter`, which lives in `Core`, so the half where the mistakes are is testable without a Windows target or a server. Three things the event names hide. A disconnect is not news of a failure, or of a success: the same one arrives for a log off, a refused password, a pulled cable and a closed tab, and only the reason code and what the session was doing at the time tell them apart — the three the documentation calls "not an error code" are the whole of the ordinary set. A logon error ends nothing; the control keeps the connection and puts a logon screen up, which is exactly what makes `M4-10` possible and what tearing the tab down here would prevent. And the failure arrives *before* the disconnect that carries it, so the router remembers — otherwise someone whose password was refused is told "Disconnected". Also: negative logon codes are not all informational, which is the tempting rule; `-1` is access denied and `STATUS_LOGON_FAILURE` is `-1073741715`, and reading the sign alone swallows both. Sunk by DISPID read from the type library, because `OnLogonError` is 22 and sits between members numbered 21 and 29 — implicit ordering would have wired the disconnect notice to whatever was declared fourth. Verified against the real control: refused connect → 1800 → Failed, bad DNS → 260 → Failed, cancel mid-connect → 1 → Disconnected. `OnConnected`, `OnLoginComplete`, `OnLogonError` and `OnFatalError` need a server that answers and go on the `M4-17` matrix
- [x] `M4-07` `ExtendedDisconnectReason` → human-readable message table — **M** — **and it turns out to be mostly not a table, which is the finding.** The obvious shape is a big switch from reason code to sentence, and writing one by hand produces confident wrong text: the codes are composed rather than enumerated, so 260, 516, 772, 1028, 1288 and 1540 all describe the same cannot-find-that-computer family, and a hand-written table is either enormous or mistaken. `GetErrorDescription(disconnectReason, ExtendedDisconnectReason)` is Microsoft's own text for Microsoft's own codes and it arrives already translated into whatever language Windows is running in — this machine answered in en-GB, "authorised" and "licence" included — and Patchbay can do neither of those things, so it does not try. **The exception is the ordinary ending, where the control is flatly wrong.** Asked about reason 1, a disconnect this computer requested, it answers "An internal error has occurred"; the same for reason 2, somebody signing out. Those are the two commonest ways a session ends, so they never reach the control at all and `SessionReasons` answers them itself — checked against `SessionSignalRouter.IsOrdinaryDisconnect` by a test that walks four thousand codes, because two places deciding the same thing is how they drift. **Both halves of a reason are read together, always**: reason 3 alone is "your session has ended, possibly for one of the following reasons" and three guesses, while reason 3 with extended reason 5 is "you have been disconnected because another connection was made to the remote computer" — passing one and not the other turns the answer back into the question. The control's strings were laid out for a message box and carry embedded newlines and doubled spaces, so they are collapsed on the way out. Logon errors are not disconnects and are never put to `GetErrorDescription`, which would answer confidently about a different failure; only the two codes this repo has pinned down get words (`-1073741715` is a refused password, `-1` a refused account) and the rest report their number, as do the fatal-error codes — a plausible sentence about a code nobody has checked is worse than a number somebody can search for, because only one of the two is obviously incomplete. `M4-10` earns more of the logon set, since it has to tell a wrong password from a locked account to know whether asking again is any use. `RdpSessionControl.CreateReasons()` is the assembled seam, reading the client late because a reason is only meaningful at the moment a session ends. Verified against the real control: 13 checks covering the codes it knows better, the four it does not, the tidying, and the pair
- [x] `M4-08` Auto-reconnect: exponential backoff, attempt cap, cancel, visible countdown — **L** — **and the finding is that the control already does half of it, better than Patchbay can.** `EnableAutoReconnect` is on by default in every generation from `IMsRdpClientAdvancedSettings2` up, and when the transport goes away for a moment the control rejoins the session it already has, using the cookie the server issued when it was established — desktop, open windows and half-typed command intact, where a fresh connect gets a new session. So there are two layers, and they cover different failures: the control's own reaches a wireless blip, and Patchbay's reaches a reboot, a gateway restart, or a laptop that was shut for an hour. **What starts a sequence is narrow and what continues one is wide**, and getting those the same way round is the whole design. Only a working session breaking starts one: an attempt that never got anywhere has somebody watching it with the failure on screen and a button underneath, and silently retrying a name that has never resolved only delays the truth. Once a sequence is running, an attempt that fails outright continues it, because a machine that is rebooting refuses connections for a minute or two before it accepts one — a sequence that stopped at the first refusal would give up exactly where it was wanted. **Nothing anybody decided is ever chased**: a disconnect that was asked for, an attempt called off, somebody signing out at the far end, and a live session that ended with no stated reason all stop it, that last one because an application that reconnects on no evidence is one whose reconnects nobody believes. **A refused sign-in is the rule that earns its keep.** It is checked before the counting, so it stops a sequence already in flight — the case is the first reconnect after a drop reaching a machine whose password has since changed, and without it the remaining nine attempts lock the account out with nobody at the keyboard. It is also the one fact a transition cannot carry, which is why `IRemoteSession` grew `LastLogonError`; everything else about an ending is the `(from, to)` pair M4-05 has carried since the beginning. Winlogon narrating itself does not count, by M4-06's rule about negative codes. **The counter resets on success**, or a connection that drops once a fortnight and recovers every time is declared exhausted after ten fortnights. Jitter is not decoration either: a gateway restarting takes every session through it down at the same instant, and without a spread they come back in lockstep, repeatedly, aimed at the machine that has just come up. It is supplied as a sample rather than drawn inside, so the arithmetic stays a function of its inputs and is tested at both ends of its range. Ten attempts at 5, 10, 20, 40 then 60 seconds is a little over seven minutes, which covers a reboot and stops well short of hammering a decommissioned server until somebody notices. The decision, the arithmetic and the countdown all live in `Core` and are tested there; the shell owns only the clock, because a visible countdown has to be redrawn on the thread that draws. Each tab measures its own elapsed time — a shared stopwatch charged a countdown that joined a clock already running for the part of the interval that passed before it existed, which cost it up to a whole second of its first wait, and the end-to-end harness is what caught it. On the control's side, `OnAutoReconnecting2` (DISPID 34) and `OnAutoReconnected` (33) are sunk and `OnAutoReconnecting` (17) deliberately is not: its third parameter is an `[out]` the control reads back to decide whether to keep trying, so implementing it makes Patchbay responsible for an answer that cannot be tested without a server that can be made to drop a live session, and answering it wrongly stops the reconnect silently. Leaving the member undeclared leaves the control's default in place, and the newer event carries strictly more — the attempt cap, and whether *this* computer is the one that went offline, which is the only form of the problem the person in front of it can fix. Neither ends anything: `SessionStateMachine.Announce` says so without a transition, because a session being held open and rejoined has not stopped. Verified in two halves. Against the real control (mstscax 10.0.26100): `EnableAutoReconnect` written both ways, accepted both ways, with nothing material refused and the disconnect wording from M4-07 still arriving intact through the enlarged sink. Against the fake, end to end through the shell: a break starting a countdown, the countdown connecting on its own, a recovery clearing the count, a machine that never answers exhausting exactly the permitted attempts, cancelling, a refused sign-in making no attempt at all, a log-off making none either, a connection with the setting off making none, and a tab closed mid-countdown taking its clock with it. What is *not* verified is the control's own reconnect firing, which needs a server that can be made to drop a live session and goes on the `M4-17` matrix
- [x] `M4-09` Certificate warning UI: subject, thumbprint, expiry, trust-once — **M** `[sec]` — **and not one of those four things can be built, which is the finding.** The control never hands the container a certificate. Nothing in the type library of `mstscax.dll` (10.0.26100.8875) exposes one — the only member with the word in its name, `PublisherCertificateChain`, signs RemoteApp publishers and says nothing about the machine at the other end — so there is no subject to show, no thumbprint to compare and no expiry to check. The trust-once button is not Patchbay's to build either: it exists, in the control's own warning, with the control's own "don't ask me again" box, and the answer kept where `mstsc.exe` keeps it. What is left is three things Patchbay can do, and all three are now done. **Choosing whether the warning appears at all** is `AuthenticationLevel` and landed with `M4-04`, where 1 is the strict value and 2 the lenient one. **Saying that a session is waiting on a person** is new: `OnAuthenticationWarningDisplayed` (DISPID 18) and `OnAuthenticationWarningDismissed` (19), both parameterless, arrive as signals the router reads without moving any state — nothing has failed and nothing has ended, the attempt is paused on a dialog, and *the dialog is inside the session's own window*, which is exactly where somebody looking at a tab that reads "Connecting…" will not think to look. The dismissal does not say which way it was answered and no member on the control says either, so the router takes its sentence back down and lets what follows speak: accepting arrives as `Connected`, refusing as an ordinary failed attempt `M4-06` already reads correctly. Inventing the missing half there would be a status bar reporting a decision nobody made. **Reporting what was actually agreed to** fills `SessionVitals.Security`, which `M4-18` left `Unknown` and `M5-17` has been waiting for. `AuthenticationType` is read-only, arrives on `IMsRdpClientAdvancedSettings6`, and is documented with four values — none, certificate, Kerberos, both — and two of the four mappings are the whole reason `RdpAuthenticationType` is a type rather than a cast. **Kerberos means network level authentication**, because Kerberos only reaches an RDP connection through CredSSP and CredSSP is what NLA is; that is not an inference about the client from a fact about the server, it is the same fact. **A certificate on its own is reported as no more than TLS**, even though NLA against a machine outside a domain runs over NTLM and is indistinguishable from here — the field is read as an assurance, so it under-reports on purpose and withholds what it cannot demonstrate. **And zero is read as "the engine did not say" rather than as legacy RDP security**, which is what the documentation calls it, because zero is also what the property reads before anything has connected and there is no server here to tell those two apart; guessing wrong would put a red badge on every session, and an alarm that is always wrong is one people stop seeing. `M5-17` already writes the muted case correctly, so nothing above had to change. **The one hook that does carry server identity is deliberately not taken.** `OnReceivedTSPublicKey` (DISPID 16) hands over the server's raw public key with an `[out]` the control reads back to decide whether to continue — the same shape as `OnAutoReconnecting`, refused for the same reason and then some. Answering it wrongly refuses every server or waves every server through, both without a sound; it cannot be tested without a server; and a public key is not a certificate, so the dialog it would permit could say no more than the control's own already does. Undeclared, the control goes on checking certificates the way `mstsc.exe` does, which is the behaviour to want by default. Verified against the real control: `AuthenticationType` present on `AdvancedSettings9`, a write to it refused, reading 0 before a connection, a session that never connected reporting no layer, and the sink still delivering `Connecting → Failed` with the control's own wording after being grown by two members — 36 checks, none failing. What is not verified is what a live session reports, which needs a server and is on the `M4-17` matrix

What is genuinely new is three things only this layer can do. **A session cannot connect until something has given it a window** — the control has no COM object until its handle exists and no handle until it is in a window that is on screen, and the shell adds a tab and connects it in one go while WPF realises the tab a moment later. So `ConnectAsync` waits for the handle, and waiting is what makes it work: awaiting yields the dispatcher, which is precisely what lets the realisation happen. Waiting forever would not, so it gives up after ten seconds and says that the session never appeared on screen. **An event-driven control is made awaitable** by a `TaskCompletionSource` the state machine completes — Connected returns, Failed throws, and Disconnected *cancels*, because an attempt somebody called off is not a failure and reporting one would offer a retry to a person who changed their mind. Cancellation goes out through the control's own `Disconnect` rather than being resolved locally, so the ending arrives as an ordinary disconnect that every listener sees the same way. Settings are applied before `Connect` and never after: the control reads most of them once as the connection is made, and applying them to a live session succeeds and does nothing. **`IHostedSessionView` is the seam for the window** — `Core` may not name a WinForms control, so the session declares it in `Patchbay.Rdp` and the shell, which references both, is the only place the two meet; a session that does not implement it is not broken, it is the fake. `SessionSurface` binds to the session and finds its own window, rather than something outside handing one over at a moment nobody can name. Vitals report the resolution, which is a real measurement, and leave the rest unknown: the negotiated security layer belongs with `M4-09` and the round trip with `M5-18`, and filling either from the request is the one thing `M5-17` says the status bar must never be told. The host is chosen at startup and falls back to the fake, so a machine with no usable control still gets a tree, an editor and an import. Verified end to end against the real control: the real host selected, a tab opened, its window attached and handled, a connect to an unresolvable name ending in Failed carrying the control's own sentence rather than a number, all 12 settings applied with nothing material refused, the sizing toggle reaching the pane, and the tab closing without taking anything with it. A session that actually comes up needs a server and is on the `M4-17` matrix
